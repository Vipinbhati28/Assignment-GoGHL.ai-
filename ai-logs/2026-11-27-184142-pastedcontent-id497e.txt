  1. Data model

  Principle: MongoDB is the source of truth for anything that must survive kill
  -9. That includes inbound messages, the outbound queue and its leases, and the
  WebSocket frame log. Redis only holds things that can be lost or rebuilt:
  rate-limit state, seq counters, sessions, OIDC login state and pub/sub.

  Change from the prompt: the reply queue and its leasing live in MongoDB, not
  Redis. A Redis list plus a lease means two stores to keep consistent, and
  Redis isn't durable here. One Mongo findOneAndUpdate claims the job and takes
  the lease in a single atomic step.

  MongoDB collections

  Collection: messages
  Key fields: workspace, contact, direction ('in'/'out'), pigeon_id,
    client_ref, text, occurred_at, status, status_rank, created_at + outbox
    fields for outbound: send_state ('pending'/'inflight'/'done'/'dead'),
    attempts, next_attempt_at, lease_owner, lease_until
  Indexes: unique {workspace, pigeon_id} partial direction:'in' · unique
    {workspace, client_ref} partial direction:'out' · {workspace, contact,
    occurred_at, pigeon_id} (thread order and snapshot) · {send_state,
    next_attempt_at} and {send_state, lease_until} (dispatcher)
  ────────────────────────────────────────
  Collection: conversations
  Key fields: workspace, contact, assignee, state ('open'/'closed'),
    last_activity_at
  Indexes: unique {workspace, contact} · {workspace, last_activity_at:-1, _id}
    (inbox pagination)
  ────────────────────────────────────────
  Collection: ws_events
  Key fields: workspace, seq, key, type, payload, created_at
  Indexes: unique {workspace, seq} (replay) · unique {workspace, key} (one
    frame per fact, e.g. in:<pmsg>, st:<ref>:<status>) · TTL on created_at (24
    h)

  Indexes are created at boot, before /healthz returns 200. /__grader/reset runs
  deleteMany on each collection rather than drop, so another instance never
  runs without its unique indexes.

  Redis keys

  Key: rl:{ws}
  Type / TTL: hash {tokens, ts}
  Purpose: Token bucket, run by a Lua script that uses Redis TIME so all
    instances share one clock. Set slightly below Pigeon's limit (≈7 burst,
    3.5/s) to allow for skew.
  ────────────────────────────────────────
  Key: cool:{ws}
  Type / TTL: string, PX = Retry-After × 1000
  Purpose: Set on any 429. The same Lua script refuses a token while this key
    exists.
  ────────────────────────────────────────
  Key: brk:{ws}
  Type / TTL: string, PX ≈ 1000–2000
  Purpose: Circuit breaker on 503 or timeout. It keeps an outage to about one
    probe per second per workspace (the check penalises more than 6 requests/s
    during an outage).
  ────────────────────────────────────────
  Key: seq:{ws}
  Type / TTL: INCR
  Purpose: Monotonic frame seq. Gaps are fine; it only needs to go up.
  ────────────────────────────────────────
  Key: sess:{id}
  Type / TTL: hash, TTL 8 h
  Purpose: Session: sub, workspaces[]. Kept on reset.
  ────────────────────────────────────────
  Key: oidc:{state}
  Type / TTL: string, TTL 10 min, GETDEL
  Purpose: PKCE verifier and nonce. Needed because /auth/login and
    /auth/callback can reach different instances through the load balancer.
  ────────────────────────────────────────
  Key: channel events:{ws}
  Type / TTL: pub/sub
  Purpose: Fan-out of new frames to every instance's sockets. Uses a dedicated
    subscriber connection.
  ────────────────────────────────────────
  Key: channel outbox:wake
  Type / TTL: pub/sub
  Purpose: Wakes dispatchers right after a reply is stored. They also poll
    every ~500 ms.

  3. Edge cases and how the design handles them

  #: 1
  Edge case: HMAC over the raw body
  Handling: Use the raw Buffer from express.raw, never re-serialised JSON.
    Compute HMAC-SHA256 of `${t}.${body}`. Check the hex length first, then
    timingSafeEqual. A missing or malformed header, or a mismatch, returns
    401, never 5xx. The whole handler is wrapped so a DB error during
    verification can't turn into a 5xx for a forged request.
  ────────────────────────────────────────
  #: 2
  Edge case: 5-minute window
  Handling: Reject when abs(now − t) > 300. The manual says "more than five
    minutes from now", so far-future timestamps are rejected too. Replayed
    events (stale_* ids) get 401.
  ────────────────────────────────────────
  #: 3
  Edge case: Parse order (level 4)
  Handling: Signature first, then JSON.parse. A body that won't parse returns
    400. Unknown workspace, unknown type, or a status for an unknown
    client_ref all return 2xx and are ignored.
  ────────────────────────────────────────
  #: 4
  Edge case: At-least-once and duplicates
  Handling: Inbound uses updateOne(upsert, $setOnInsert) on the unique
    {workspace, pigeon_id}. A duplicate is a no-op and still gets 2xx. The
    frame is keyed in:<pmsg>, so a crash between the two writes plus a retry
    still yields exactly one frame.
  ────────────────────────────────────────
  #: 5
  Edge case: occurred_at ordering
  Handling: Never rely on arrival order. The thread, the snapshot inbound list
    and the UI all sort by (occurred_at, pigeon_id). last_activity_at uses
    $max.
  ────────────────────────────────────────
  #: 6
  Edge case: Status out of order (delivered before sent)
  Handling: Ranks: queued 0, sent 1, delivered/failed 2. The update filter is
    status_rank < newRank, so status never goes backwards, and the first final
    status wins.
  ────────────────────────────────────────
  #: 7
  Edge case: Ack within 5 s, p95 < 1 s
  Handling: Two indexed writes plus one INCR, then 200 after the write is
    acknowledged (j:true). Never return 2xx before the write lands. That rule
    is what makes kill -9 during the flood safe, because Pigeon retries for
    about 22 s.
  ────────────────────────────────────────
  #: 8
  Edge case: client_ref idempotency (even two identical requests at the same
    instant)
  Handling: Insert the outbound doc. The unique {workspace, client_ref} turns
    the loser's insert into E11000, and both requests get 202. The
    conversation is upserted so a reply to a contact who hasn't written yet
    still works. 202 is sent only after the durable insert.
  ────────────────────────────────────────
  #: 9
  Edge case: Exactly-once to Pigeon
  Handling: Every send carries Idempotency-Key: <workspace>:<client_ref>. A
    retry after a timeout, crash or failover reuses the key, so Pigeon returns
    the original result and doesn't send again.
  ────────────────────────────────────────
  #: 10
  Edge case: 12 s slow accept
  Handling: Client timeout ≈ 4 s. The outcome is then unknown, so the job
    keeps inflight and is retried later with the same key. The retry is
    delayed past ~13 s so it doesn't overlap the still-pending original. I'll
    confirm in pigeon/ source how a repeated key behaves while the first call
    is still in flight. The status webhook may arrive before or instead of the
    HTTP response; that's fine because status updates don't depend on send
    state.
  ────────────────────────────────────────
  #: 11
  Edge case: Retry-After / per-workspace limit across instances
  Handling: Every send first takes a token from the shared Lua bucket. On 429
    it sets cool:{ws}. A job that gets no token is released with
    next_attempt_at = now + wait without spending an attempt. Because the
    state is in Redis, two instances can't each spend their own 8-token
    bucket.
  ────────────────────────────────────────
  #: 12
  Edge case: Outage (all 503s)
  Handling: The brk:{ws} breaker plus per-job exponential backoff, capped at
    about 2 s so recovery is noticed quickly. Jobs remain pending, never dead,
    for 503 or timeout.
  ────────────────────────────────────────
  #: 13
  Edge case: Lease reclaim after kill -9
  Handling: The dispatcher atomically claims {pending, next_attempt_at ≤ now}
    OR {inflight, lease_until < now}, setting lease_owner = instanceId and
    lease_until = now + 20s. The 20 s lease is longer than the 12 s slow
    accept plus timeout. A restarted or surviving instance picks the job up
    within about 20 s, inside the 60 s failover window, and the
    Idempotency-Key makes the re-send safe.
  ────────────────────────────────────────
  #: 14
  Edge case: Six-way claim race
  Handling: First upsert $setOnInsert the conversation (retrying once on
    E11000), then findOneAndUpdate({ws, contact, assignee ∈ {null, agent}},
    {$set:{assignee: agent}}). A match returns 200 and emits
    conversation.assigned; no match returns 409. It's one atomic document
    operation, so it holds across instances.
  ────────────────────────────────────────
  #: 15
  Edge case: WS seq rising across instances
  Handling: Two instances can publish seq 42 before 41. Each socket tracks
    lastSent, drops frames with seq ≤ lastSent, and on a gap waits about 300
    ms, then backfills from ws_events.
  ────────────────────────────────────────
  #: 16
  Edge case: WS replay (after=)
  Handling: Subscribe first and buffer live frames, then query ws_events for
    seq > after, send them, then flush the buffer deduplicated by seq. This
    avoids the gap between the query and the subscription. The workspace
    filter on every query keeps tenants apart.
  ────────────────────────────────────────
  #: 17
  Edge case: Login across instances
  Handling: PKCE state lives in Redis (oidc:{state}, GETDEL, single use). The
    session cookie is opaque, HttpOnly and SameSite=Lax. After the callback
    the user is redirected to WEB_ORIGIN. The harness stops following
    redirects once it leaves :4000, so that's fine.

  What pigeon/server.js showed: Pigeon stores the Idempotency-Key response
  before its 12-second slow reply, and it checks for repeats before the outage
  and rate-limit checks. So after my 4-second client timeout, it's safe to retry
  almost at once with the same key. The retry gets the original answer and
  doesn't count against the rate limit. Its limits are a bucket of 8 refilling
  at 4/s, and a 2-second cool-off after a 429.

  Two changes from the approved plan:
  - Lease is 10 s, not 20 s. Pigeon's behaviour means a lease only needs to
    outlast one 4-second HTTP attempt. A shorter lease means a dead instance's
    replies are picked up sooner.
  - Duplicate events are checked before taking a seq number. Otherwise duplicate
    webhooks would leave gaps in the numbering, and each gap holds back live
    WebSocket delivery for 300 ms.
